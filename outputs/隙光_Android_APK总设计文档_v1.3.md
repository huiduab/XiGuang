# 隙光 Android APK 总设计文档

版本：v1.3  
日期：2026-07-28  
状态：产品定义稿，可进入交互原型阶段  
正式产品名：隙光

---

## 1. 文档目的

本文档定义一款小巧、轻快、以本地数据为主的 Android APK 应用。软件每天自动获取用户订阅的博客更新和指定 X 账号的新推文，将新增内容汇总后通过 Android 系统通知提醒，并持续记录未读、已读、收藏和归档状态。

本文档中的“博客汇总”按用户原文“博客胡总”的含义推定。

---

## 2. 产品定义

### 2.1 一句话定义

一个由用户自己控制的个人信息收件箱：在空闲时用高质量订阅内容替代算法短视频，持续关注少量重要人物和来源，明确记录尚未阅读的信息，并将有价值的内容保存到自定义文件夹。

### 2.2 核心价值

1. 不依赖社交平台的推荐算法。
2. 不遗漏指定人物和博客的更新。
3. 清楚区分未读、已读和已保存内容。
4. 通知消失后，内容仍然保留在软件中。
5. 用户可以建立自己的两级文件夹体系。
6. 默认将数据保存在本地，支持备份和导出。
7. 用户主动打开应用，而不是依赖产品制造提醒和注意力焦虑。
8. 内容按时间和用户选择呈现，不提供无限算法推荐。

### 2.3 目标用户

- 只关注少数高价值作者、专家或行业人物的个人用户。
- 需要长期追踪研究对象的创作者、研究者和投资者。
- 不希望每天打开多个网站和社交平台检查更新的人。
- 重视数据所有权，希望建立私人信息库的人。

### 2.4 第一版非目标

- 不做公共社区和用户互相关注。
- 不做内容推荐算法。
- 不做社交媒体发布和账号运营。
- 不做企业舆情分析。
- 不做无限层级的知识管理系统。
- 不在第一版自动保存所有网页全文。
- 不在第一版提供手机端和多设备同步。

### 2.5 替代短视频的体验原则

- 首页提供数量有限、可完成的“今日待读”，不制造无限推荐流。
- 内容默认按发布时间排列，不根据停留时间和点击行为操纵排序。
- 列表底部明确显示“今天的新内容已经看完”。
- 不自动播放视频、音频或连续切换下一条。
- 展示预计阅读时间和今日阅读进度，但不设计打卡焦虑或连续登录惩罚。
- 用户看完新增内容后，可进入收藏和文件夹继续深度阅读。
- X 的点赞、转发等热度数字不是主要排序依据。

### 2.6 品牌与视觉系统

产品名“隙光”来自“缝隙里的光”：用户把原本可能交给短视频的碎片时间，重新用于阅读真正重要的内容。

品牌关键词：

- 安静。
- 清醒。
- 精确。
- 私人。
- 有限阅读。

App 图标由两片抽象书页构成，中间负空间形成一束狭窄的光，同时暗示书签和时间缝隙。图标不直接使用 RSS、X、播放按钮、灯泡或 AI 星光等常见符号。

视觉原则：

- 参考苹果式的克制、排版尺度、留白和材质精度，但保持 Android 交互规范。
- 浅色主题使用暖雾石色而非纯白色。
- 深色主题使用石墨与烟灰色而非纯黑色。
- 强调色使用氧化铜、矿物蓝、鼠尾草绿和低饱和梅紫。
- 主要依靠文字层级、细分隔线、缩进和少量色标组织内容。
- 避免满屏圆角卡片、过量毛玻璃、彩色渐变、AI 星光和数据仪表盘造型。

## 3. 核心概念

### 3.1 项目 Project

项目是一组数据来源的集合，并拥有独立的推送启用与失败暂停状态。具体每日推送时间由应用“设置”统一管理。

示例：

- “AI 人物动态”：5 个 X 账号、3 个博客。
- “设计灵感”：8 个博客。
- “重点观察”：2 个 X 账号。

每个项目拥有独立的：

- 名称、图标和颜色。
- 数据来源。
- 是否参与每日汇总。
- 推送启用/暂停状态。
- 未读数量。
- 最近采集和最近推送状态。

### 3.2 数据来源 Source

第一版支持两类来源：

1. 博客：RSS、Atom 或 JSON Feed。
2. X：指定公开账号的帖子时间线。

来源属于一个项目。后续版本可增加 Newsletter、YouTube、播客和普通网页监测。

### 3.3 内容条目 Item

内容条目是一次采集得到的一篇文章或一条 X 帖子。

条目状态包括：

- 未读。
- 已读。
- 稍后读。
- 已收藏。
- 已保存到文件夹。
- 已归档。
- 已隐藏。

“已读”和“已保存”是两个独立维度。已读内容仍然可以收藏或保存；已保存内容也可以保持未读。

### 3.4 用户文件夹 Folder

用户可以像管理文件一样创建文件夹，用于长期保存内容。

第一版最多支持两级：

```text
一级文件夹
└── 二级文件夹
```

示例：

```text
人工智能
├── 模型发布
└── 产品案例

人物观察
├── Sam Altman
└── Elon Musk
```

规则：

- 文件夹和数据来源分类互相独立。
- 一个条目可以保存到一个主文件夹。
- 第一版允许为条目附加多个标签，但不允许同时存在于多个实体文件夹，避免重复与删除歧义。
- 移动条目只改变保存位置，不影响阅读状态。
- 删除文件夹时必须选择“将内容移到上一级”或“移到未分类”，不得默认删除内容。

### 3.5 标签 Tag

标签用于跨文件夹的轻量分类，例如“重要”“待研究”“产品灵感”。标签不是第一版的核心导航结构，但属于 P1 功能。

## 4. 产品信息架构

```text
今日
├── 今日摘要
├── 全部未读
└── 推送异常

项目
├── 项目 A
│   ├── 全部内容
│   ├── 博客
│   └── X
└── 项目 B

信息库
├── 收藏
├── 稍后读
├── 未分类
└── 用户文件夹
    ├── 一级文件夹
    └── 二级文件夹

来源
├── 博客
└── X 账号

通知记录

设置
```

系统分类和用户分类形成两个不同维度：

| 分类维度 | 用途 | 是否可由用户修改 |
|---|---|---|
| 博客 / X | 表示内容从哪里获取 | 否 |
| 项目 | 决定一组来源如何采集和推送 | 是 |
| 一级 / 二级文件夹 | 决定内容如何长期保存 | 是 |
| 标签 | 跨文件夹补充描述 | 是 |

## 5. 核心用户流程

### 5.1 首次使用

1. 安装并打开软件。
2. 直接进入应用；通知默认关闭，不在首次启动时请求通知权限。
3. 创建第一个项目。
4. 添加博客地址或 X 用户名。
5. 默认使用“仅打开应用时刷新”；用户以后可在设置中主动开启定时推送。
6. 软件执行首次采集。
7. 用户进入今日页面查看结果。

### 5.2 默认模式：打开应用时刷新

1. 应用默认不注册周期后台任务，也不在后台主动请求网络。
2. 用户打开应用时自动刷新所有启用项目。
3. 用户也可以下拉或点击“立即刷新”。
4. 刷新后完成标准化、去重并写入未读列表。
5. 如果发现新内容，应用前台显示“新增 8 条内容”的摘要提示。
6. 因为用户已经位于应用内，默认不发送系统通知。
7. 如果刷新失败，显示来源错误，不将项目标记为“推送失败暂停”。

### 5.3 可选模式：设置了全局推送时间

1. 后台调度器到达采集时间。
2. 获取项目中的博客和 X 更新。
3. 对内容进行标准化、去重和排序。
4. 写入本地数据库并标记为未读。
5. 到达推送时间后生成项目摘要。
6. Android 显示系统通知。
7. 用户点击通知，软件打开对应项目的未读列表。

通知示例：

> AI 人物动态有 8 条新内容  
> 3 篇博客文章 · 5 条 X 帖子  
> 查看更新

### 5.4 阅读与保存

1. 用户打开未读内容。
2. 内容可在客户端内预览，或打开原始网页。
3. 根据设置，在打开时或手动操作后标记已读。
4. 用户可以收藏、稍后读或保存到文件夹。
5. 保存时选择一级文件夹或二级文件夹。
6. 已读条目降低视觉强调，但仍可搜索和访问。

### 5.5 定时推送失败

1. 系统尝试发送项目摘要。
2. 一次推送任务最多快速重试 3 次。
3. 仍失败则将该项目的通知状态改为“因失败暂停”。
4. 暂停后不继续反复发送通知，避免持续报错。
5. 后台内容采集继续运行，新增内容仍进入未读列表。
6. 应用图标角标和今日页面显示异常标记。
7. 用户可以执行“测试推送”。
8. 测试成功后，用户确认恢复该项目推送。

重要区分：

- 推送失败：暂停项目的通知发送，继续采集。
- 没有设置推送时间的项目不存在后台推送失败状态，只记录刷新或来源错误。
- 单个来源采集失败：暂停或降频该来源，不暂停项目中的其他来源。
- X 授权失效：暂停 X 来源并要求重新授权。
- 应用被用户从系统设置中“强制停止”：Android 会停止后台任务；用户再次打开应用后执行补采并重新调度。

## 6. 功能需求

优先级定义：

- P0：第一版必须完成。
- P1：第一版完成后优先增加。
- P2：后续增强功能。

### 6.1 项目管理

| 编号 | 优先级 | 需求 |
|---|---:|---|
| PRJ-01 | P0 | 创建、编辑、暂停、恢复和删除项目 |
| PRJ-02 | P0 | 项目包含名称、颜色、图标、来源和是否参与每日汇总 |
| PRJ-03 | P0 | 显示每个项目的未读数量、最近采集时间和最近推送结果 |
| PRJ-04 | P0 | 项目可以加入或退出全局每日汇总 |
| PRJ-05 | P0 | 项目暂停推送时继续采集内容 |
| PRJ-06 | P0 | 删除项目之前显示来源数量和保存内容影响 |
| PRJ-07 | P1 | 复制项目及其设置 |
| PRJ-08 | P1 | 项目排序和置顶 |

### 6.2 博客来源

| 编号 | 优先级 | 需求 |
|---|---:|---|
| SRC-B01 | P0 | 用户粘贴网站或 Feed 地址后自动发现 RSS/Atom |
| SRC-B02 | P0 | 保存来源名称、网站地址、Feed 地址、图标和最后同步位置 |
| SRC-B03 | P0 | 解析标题、作者、发布时间、摘要、封面和原文地址 |
| SRC-B04 | P0 | 依据 GUID、规范化 URL 和内容指纹去重 |
| SRC-B05 | P0 | 支持手动“立即同步” |
| SRC-B06 | P0 | 显示同步成功、失败、暂停和授权异常状态 |
| SRC-B07 | P1 | 支持 JSON Feed |
| SRC-B08 | P1 | 对只提供摘要的 Feed 提取网页正文 |
| SRC-B09 | P2 | 为没有 Feed 的普通网页生成监测规则 |

### 6.3 X 来源

| 编号 | 优先级 | 需求 |
|---|---:|---|
| SRC-X01 | P0 | 添加公开 X 用户名或主页地址 |
| SRC-X02 | P0 | 通过官方 X API 获取该用户新发布的帖子 |
| SRC-X03 | P0 | 使用 `since_id` 增量获取，避免重复读取和费用浪费 |
| SRC-X04 | P0 | 默认只收集原创帖子并排除回复与转发；用户可在来源设置中单独开启 |
| SRC-X05 | P0 | 保存帖子 ID、文本、发布时间、作者、媒体摘要和原文链接 |
| SRC-X06 | P0 | 显示授权失效、额度不足、限流和账号不可访问状态 |
| SRC-X07 | P0 | X 错误不得阻塞同一项目中的博客采集 |
| SRC-X08 | P1 | 将同一线程合并显示 |
| SRC-X09 | P1 | 显示引用帖子和附件预览 |
| SRC-X10 | P2 | 支持 X 列表和关键词搜索 |

### 6.4 采集与调度

| 编号 | 优先级 | 需求 |
|---|---:|---|
| SCH-01 | P0 | 用户设置全局推送时间后，每天在该时间附近执行一次后台采集与汇总 |
| SCH-01A | P0 | 全局推送时间默认为空，不创建周期后台任务 |
| SCH-02 | P0 | 支持启动后补采上次运行以来的内容 |
| SCH-02A | P0 | 打开应用时自动刷新，但距离上次成功同步不足 15 分钟时复用本地数据，降低流量与 X API 成本 |
| SCH-03 | P0 | 所有采集任务必须幂等，重复执行不得产生重复条目 |
| SCH-04 | P0 | 网络断开时指数退避，不持续高频请求 |
| SCH-05 | P0 | 记录每次采集开始时间、结束时间、结果和错误类型 |
| SCH-06 | P0 | 支持按来源手动同步 |
| SCH-06A | P0 | 未设置全局推送时间时，打开应用即刷新所有启用项目 |
| SCH-07 | P1 | 支持 15 分钟、30 分钟、1 小时和自定义频率 |
| SCH-08 | P1 | 支持免打扰时间 |

### 6.5 未读与内容状态

| 编号 | 优先级 | 需求 |
|---|---:|---|
| ITM-01 | P0 | 新采集内容默认标记为未读 |
| ITM-02 | P0 | 支持标记已读、恢复未读和批量全部已读 |
| ITM-03 | P0 | 已读内容使用低强调样式，未读内容使用高强调样式 |
| ITM-04 | P0 | 打开内容是否自动已读由用户设置 |
| ITM-05 | P0 | 收藏、稍后读和已读状态互不覆盖 |
| ITM-06 | P0 | 内容被保存到文件夹后仍保留来源和项目关系 |
| ITM-07 | P1 | 支持隐藏内容和撤销操作 |
| ITM-08 | P1 | 检测文章编辑并显示“已更新” |

### 6.6 文件夹与信息库

| 编号 | 优先级 | 需求 |

| NTF-03 | P0 | 点击通知打开对应项目的未读列表 |

## 7. 界面设计

### 7.1 主窗口布局

## 10. 技术方案

### 10.1 推荐技术栈

- 开发语言：Kotlin。
- 用户界面：Jetpack Compose + Material 3。
- 架构：单 Activity、MVVM、Repository。
- 本地数据库：Room + SQLite。
- 设置存储：DataStore。
- 后台任务：WorkManager。
- 并发：Kotlin Coroutines + Flow。
- 网络：OkHttp 或 Ktor Client。
- RSS 解析：轻量 XML/Feed 解析库。
- 系统通知：Android NotificationManager。
- 密钥保护：Android Keystore + 加密存储。
- 安装方式：签名 APK；后续可同时发布 AAB 到应用商店。

选择理由：

- 原生 Kotlin/Compose 避免额外跨平台运行层，更符合“小巧、轻快、Android 优先”的目标。
- WorkManager 是 Android 推荐的可延迟、可持久化后台工作机制。
- Room 提供 SQLite 上的结构化访问、迁移与编译期查询检查。
- 原生通知、Deep Link、后台任务和电池策略的兼容性优于 WebView 客户端。

### 10.2 APK 架构

```text
Jetpack Compose 用户界面
        │
ViewModel + StateFlow
        │
Repository / Use Cases
├── 项目服务
├── 来源连接器
│   ├── RSS 连接器
│   └── X API 连接器
├── WorkManager 调度器
├── 去重与标准化
├── Android 通知服务
├── 搜索与文件夹服务
└── 备份与诊断
        │
        ▼
Room / SQLite 本地数据库
```

### 10.3 Android 本地后台限制

第一版采用 Local-first：

- 内容和阅读状态保存在手机本地。
- WorkManager 在系统允许的后台时间窗口执行采集。
- 周期任务不是精确闹钟，可能因为 Doze、省电模式和厂商后台限制而延迟。
- WorkManager 的周期任务最短周期为 15 分钟，但本产品默认按每日或数小时级别调度。
- 应用被系统强制停止后，在用户重新打开应用前不保证继续采集。
- 用户再次打开应用时补采遗漏时间段。

Android 官方说明，周期 WorkManager 任务会受到省电优化和 Doze 影响，适合能够接受执行时间不完全精确的任务。[Android PeriodicWorkRequest](https://developer.android.com/reference/androidx/work/PeriodicWorkRequest)、[Doze 与 App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby)

如果未来要求“即使应用长期未打开，也要在指定时间稳定收到通知”，需要增加云端采集器，并通过 Firebase Cloud Messaging 将摘要发送到 APK。FCM 可以在应用处于后台时把通知交给 Android 系统通知栏。[Android FCM 消息接收](https://firebase.google.com/docs/cloud-messaging/android/receive-messages)

### 10.4 X 可行性

X 官方 API 提供指定用户帖子时间线，并支持 `since_id` 增量获取、排除回复和转发。当前接口按使用量计费，因此必须：

- 每个来源保存最后帖子 ID。
- 避免重复请求已经读取的内容。
- 限制默认采集频率。
- 提供月度用量与预算警告。
- 在额度不足时暂停 X 来源而不是重复失败。

参考：[X 用户时间线](https://docs.x.com/x-api/posts/timelines/introduction)、[X API 概览](https://docs.x.com/x-api/overview)

### 10.5 Android 通知可行性

第一版本地模式由 WorkManager 完成采集后创建 Android 通知。通知点击后通过 Deep Link 打开对应项目。

应用通知模式：

- `on_open`：默认模式；全局时间为空，不请求通知权限、不注册周期任务，只在打开应用或手动刷新时采集，并显示应用内新增摘要。
- `scheduled`：用户主动开启定时推送并填写全局时间后，应用请求通知权限，只注册一项每日后台任务，汇总所有参与推送的项目。

“推送失败”在本地模式下定义为：

- 通知权限未授予。
- 项目通知渠道被关闭。
- 创建通知时发生系统或应用错误。

本地通知无法证明用户一定看到了通知，只能确认应用是否成功提交给 Android 通知系统。若通知权限全局不可用，应暂停所有项目通知并在应用内显示统一修复入口；若只有一个项目的通知任务异常，则只暂停该项目。

## 11. 非功能需求

### 11.1 性能目标

- 冷启动目标：1.5 秒内显示主界面。
- 空闲内存目标：120 MB 以内。
- 空闲 CPU：接近 0%，不得持续轮询。
- APK 目标：20 MB 以内，具体以正式构建、ABI 和资源压缩结果验证。
- 5 万条内容下常用列表查询低于 200 ms。
- 采集任务不得阻塞界面操作。
- 长列表使用 Compose LazyColumn 等惰性渲染组件。

以上为产品验收目标，不是框架保证值。

### 11.2 可靠性

- 采集、去重和通知任务必须可重复执行。
- 崩溃后不得损坏数据库。
- 任务中断后，下次启动可以继续。
- 数据库变更使用迁移脚本。
- 自动备份采用轮换策略。

### 11.3 安全与隐私

- X 令牌不得以明文写入数据库或日志。
- 所有外部内容在界面中渲染前进行清理。
- 默认阻止外部网页脚本在阅读视图中执行。
- 日志中隐藏 Token、Cookie 和用户隐私信息。
- 删除数据时区分移入回收状态与永久删除。
- 用户可以完整导出自己的数据。

### 11.4 可访问性

- 全部核心功能支持键盘。
- 未读状态不只用颜色表达。
- 支持系统深色模式和缩放。
- 通知与异常信息使用清晰文本。

## 12. 异常与边界场景

必须设计并测试：

1. RSS 地址重定向或域名变更。
2. Feed 返回格式错误。
3. 同一文章改变标题或发布时间。
4. 博客一次补发大量旧文章。
5. X 用户改名。
6. X 帖子被删除或编辑。
7. X 账号变为私密、被封禁或不存在。
8. X API 限流、额度不足或授权过期。
9. 手机在推送时间处于 Doze、低电量或厂商深度省电状态。
10. Android 通知权限或项目通知渠道被用户关闭。
11. 用户在系统设置中强制停止应用。
12. 全局推送时间为空时，应用不得残留周期后台任务。
13. 文件夹重名。
14. 删除含有内容的文件夹。
15. 系统时间或时区发生变化。
16. 数据库空间不足。
17. 备份恢复到旧版本。
18. 同一内容从多个来源出现。

## 13. MVP 验收标准

第一版可以发布测试的条件：

1. 用户可以创建至少 10 个项目。
2. 每个项目可以同时包含博客和 X 来源。
3. RSS 新文章能够稳定增量获取且不重复。
4. X 新帖子能够通过官方 API 增量获取。
5. 每日汇总能正确统计博客和 X 数量。
6. Android 通知点击后能打开正确项目。
7. 一次推送任务连续失败后项目自动进入暂停状态。
8. 推送暂停后仍继续采集新内容。
9. 用户可以测试并手动恢复推送。
10. 未读、已读、收藏和稍后读状态不会互相覆盖。
11. 用户可以创建一级和二级文件夹，但不能创建第三级。
12. 删除文件夹不会静默删除其中内容。
13. 搜索和筛选可以覆盖至少 5 万条内容。
14. 软件重启后全部状态保持一致。
15. 应用能检测通知权限和通知渠道异常，并明确引导用户修复。
16. 数据可以备份、恢复和导出。
17. 全局推送时间为空时，应用不会注册周期后台任务。
18. 全局推送时间为空时，打开应用会刷新全部启用项目并显示新增内容摘要。
19. 全新安装后通知默认关闭，并且不会立即请求通知权限。

## 15. 主要风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| X API 费用或政策变化 | X 采集不可用或成本上升 | 连接器独立、预算限制、允许替换数据提供方 |
| Doze、强制停止或厂商省电 | 后台采集与通知延迟 | WorkManager、启动补采、权限诊断；后续云端 + FCM |
| RSS 质量不一致 | 摘要缺失或重复 | 多级去重、容错解析、来源状态提示 |
| Android 通知被禁用 | 用户误以为无更新 | 检测权限与通知渠道，今日页面显示修复入口 |
| 本地数据库损坏 | 私人信息丢失 | 事务、完整性检查、自动备份和恢复点 |
| 内容版权 | 不适合无限保存全文 | 第一版默认保存标题、摘要、链接和个人笔记 |
| 文件夹与项目混淆 | 用户不知道内容在哪里 | 项目负责采集，文件夹负责保存，界面保持分区 |

## 16. 已确定的产品决策

1. 第一版交付为可安装的 Android APK。
2. 技术方向为小型、原生、Local-first Android 应用。
3. 数据来源第一版只做博客和 X。
4. 项目负责采集与推送策略。
5. 系统按博客/X 对来源分类。
6. 用户文件夹最多两级。
7. 推送失败后暂停项目通知，但继续采集。
8. 单个来源失败不得阻塞整个项目。
9. 应用被系统强制停止后不承诺后台运行，重新打开时补采。
10. 用户在设置中填写全局推送时间时，应用只创建一项每日周期后台任务。
11. 全局推送时间为空时，仅在打开应用或手动刷新时采集。
12. 通知默认关闭，用户主动开启后才申请权限。
13. 产品承担“用主动、高质量阅读替代被动刷短视频”的角色。
14. X 默认只收集原创帖子，回复与转发按来源单独开启。
15. 第一版优先解决可靠获取、未读追踪和保存，不优先增加 AI。
